## 1. 结论与证据

核心问题是输入组织、调度粒度和失败传播。增加顶层 workers 无法把一个巨大的串行请求变成并行任务，也不能修复超长输入。

| 实际阶段 | 墙钟时间 | 本轮结果 |
|---|---:|---|
| generate | 30分02秒 | 新完成0、复用29、失败6；3个Checklist超时，3个review_dynamics缺输入 |
| evaluate | 66分45秒 | 新完成7、复用103、失败115 |
| recheck | 43分28秒 | 完整完成0；4篇因缺输入失败，剩余1篇运行至用户停止 |

最新一轮可解析调用记录共36条，28次成功、6次超时、2次其他失败。其中一个融合请求明确返回 input_too_large：实际1,090,128字符，上限1,048,576字符；最后一个复核请求在用户终止期间退出，不能归为自然超时。

复核成功17次调用累计输入5,039,822 tokens，调用耗时合计约39分19秒。每次输入约25万—31万 tokens。最终论文结果未完成，并不代表中间步骤没有工作；但这种输入与串行执行方式代价过高。

停滞附近日志记录可用内存约18 GiB、调度上限64、实际只有1—3个请求，没有证据表明这些时段由内存不足限制并发。日志不能进一步判定每次超时是在服务端排队、推理还是网络等待。

## 2. 问题清单

### P0：材料重复和请求过大

1. `evidence.canonical_sources()` 为别名复制完整来源正文。一个真实片段因此以多个ID进入输入。
2. `prepare()` 同时保存顶层 manuscript 和 `MANUSCRIPT` 来源；`materials()` 又把两者同时送出。论文片段也可能与全文再次重叠。
3. `evidence_pool()` 合并原有来源、历史检索、两基线来源和原始检索记录，仅按 source_id 去重。相同正文、不同ID不会合并。
4. Graph原始观测被整体序列化为一个约18.7万字符的来源，而非按当前待核Graph断言选择事实。
5. `materials()` 被 support、quality、concerns、importance、fusion、preference、recheck 共用，缺少按评价对象组织材料的步骤。历史任务虽有类型和日期过滤，也没有请求大小预算。
6. `fusion()` 在整包材料上继续附加三方法全部断言及核验结果。复核差异解释再次携带原任务整包输入。
7. Checklist一次读取全部审稿段落与全文；最长一篇二者正文合计约30.2万字符，尚未计入结构字段、指令和schema。
8. 基线各步骤重复附带全文、来源中的全文和不断增长的 previous_steps；review_sections 按行切块且携带全部前序段落，长单行和历史累积均可突破名义块大小。
9. 格式修复把原回答与错误追加到原始大输入，没有重新计算预算。仅缩小首次请求不足以覆盖此路径。

证据示例：s41467-026-68786-6有671条来源，来源JSON约875,473字符；392条为非空 passage 的重复副本。一段1,256字符摘要出现6次。重复正文不代表可删除其出处、版本、位置或别名。

### P0：并发停留在论文/阶段层

1. Checklist没有分片；support虽按24断言分批，但批次串行，每批仍发送整池证据。
2. recheck六方法、三类重复评价、分歧解释、控制原版/改版依次执行；剩一篇时实际只占一个CLI会话。
3. 检索的查询、引文、全文下载、日期补全大量串行。GPU编码/排序需要共享与受控，但网络I/O没有必要随之串行。
4. 组内使用粗粒度wave：如extract被迫等reference及quality_checklist，尽管extract本身只需要报告、正文和core。组间全局等待可以作为脚本边界保留，组内这类非必要等待应消除。
5. 请求workers=128只是线程池规模；CPU准入上限为64，没有创造足够的独立可运行子任务。增加数字不能解决上述结构问题。

### P0：依赖失败与执行范围

1. runner不区分成功和失败地减少phase剩余数，失败结束也会释放下游。缺输入任务随后重复失败。
2. all无条件接着运行后续组及汇总，直到末尾才计算失败数。需要保留可独立完成的研究任务，但不能把依赖失败当作就绪。
3. 仅all默认pilot；generate/evaluate/recheck等独立命令默认all。用户拆开执行时容易意外扩到全体论文。
4. 独立aggregate没有队列参数，可能混入早先100篇运行产物。当前all内传入pilot集合，但拆脚本后必须统一范围。

### P1：可观测性、中断和日志

1. subprocess.run(capture_output=True)在CLI结束后才解析事件；心跳只能证明调度器还活着，不能说明模型进展。
2. 超时没有保留下完整的实时事件，临时目录随后删除；缺少请求体积、首事件时间、最后活动时间、按子任务的状态。
3. 当前停止语义允许一个CLI继续等待1800秒；超时由subprocess管理直接子进程，未显式管理CLI包装器的整个子进程组，存在残留风险，不能断言本轮已经发生。
4. 已有calls.jsonl有11行不可解析；损坏原因尚不能确定。aggregate.costs逐行直接json.loads，按当前实现会在遇到坏行时中断。不能静默补造这些调用的成本。
5. counts的分子包含失败结束项。界面虽列出了失败数，仍易把“已处理4/5”读成“成功80%”。
6. 并发若从一个进程扩展到多个脚本同时写同一路径，现有线程锁和固定.tmp文件名不能提供跨进程互斥。因此设计为脚本间顺序执行，每个脚本一个调度器。

### P1：试运行与科学结果的边界

1. 复核是h5的同模型重复评价和构造控制，不是人工真值，也不应阻断其他独立主评价任务。
2. 改为片段选择、分层读文、分批判断后，评价条件发生变化。不能自动把旧大输入结果与新结果混合后声称统一条件比较。
3. 六方法使用同一中立证据目录和相同材料组织规则。禁止只提供各方法有利的引用，或先读首轮判断再选择复核证据。
4. 缺失文件、检索失败、模型超时必须记为技术缺项，不能转成支持/不支持、无创新或偏好平局。

## 3. 修复后的输入机制

### 3.1 完整证据存储与请求材料分开

- 原始材料完整保留，不覆盖EvidenceStore、不删除旧来源、不用截断文件来缩小请求。
- 新建普通JSON证据目录：正文存一次，别名映射到正文；保留每个别名的source_id、来源类型、版本、日期、位置及原始路径。
- 文献实体优先依据现有明确ID/规范化DOI识别；仅标题相似不得合并。相同正文只共享文本存储，不据此宣称它们是同一科学来源。
- 无明确同源关系的重复正文可作为一个文本块附多个独立出处，保持不同日期、版本和证据等级。摘要不升级成全文，目标论文不变成历史证据。
- 不新增哈希、指纹或mtime闸门；去重使用现有身份关系和实际文本相等比较。
- Manuscript按章节和自然段切片，赋予普通序号和原文位置；全文及原位置留在本地。Graph事实也拆成可定位的claim/neighbor/joint事实单元。

### 3.2 所有CLI请求统一受预算约束

建议初始工程预算（不是已验证的最优参数）：

| 项目 | 规则 |
|---|---|
| 单请求序列化上限 | 指令、用户材料和输出schema合计最多60,000字符、UTF-8最多120,000字节，两者均满足 |
| 常规目标 | 明显低于硬上限；优先按对象与相关原文组织，记录可用token估算及估算方式，不把估算当精确输入tokens |
| 单原文片段 | 通常2,000—4,000字符，按段落/句子切分并保留上下文和位置 |
| 单次判断对象 | 通常1—4个复杂对象；简单断言可4—8个，最终由材料大小决定 |
| 输出大小 | 通过对象数、字段范围和分批合并控制，不能让一次输出枚举整篇全部对象 |
| 超预算 | 发起CLI前继续拆分；不得照发，不得只砍尾部，不得绕过预算走格式修复路径 |

60,000字符不是CLI官方限制；它是远低于已观察错误阈值的保守实验起点。CLI自身注入的环境说明等开销另记；上述限制约束脚本可控制的输入，不能承诺不可见服务端token数。

必须覆盖生成、查询规划、片段阅读、评价、合并、解释、控制和格式修复全部路径。合并输出再次过大时，继续分层归并；不得出现“分片完成后又把全部原文拼回一个请求”。原回答过大的格式修复也要拆分，不能直接复制整包上下文。

单次输入中相同正文只出现一次。不同独立科学判断之间允许必要的同一证据复用；AB/BA和盲法复核尤其不能为了去重共享先前判断或会话历史。减少的是无关整池输入和别名重复，不是取消独立评价所需材料。

### 3.3 选择材料且保留科学覆盖

1. 先确定当前对象、相关章节、被引来源和必要对照；从共同证据目录取原文片段。
2. 原报告引用优先定位，但必须补入同一规则选出的潜在反证、比较对象和范围限定，不能只检验报告自选来源。
3. 阅读全集的任务采用“全范围分片阅读→证据卡片→归并”：每个原文片段都有阅读记录，卡片保留精确引句与位置、反例、不确定性；后续必要时按位置回读。
4. 局部检索未找到证据不能写成全库不存在。保留已审材料、未审范围、检索失败和无法判定原因。
5. 同一论文/核心/审稿问题的中立材料包预先生成并固定给六方法；方法特有引文可补充，但规则相同，仍保留共同反证。
6. 用新材料包做复核时与新主评价使用相同材料范围，只隐藏首轮标签，避免把证据变化误当模型不稳定。
7. 同一科学对象的分片结论出现冲突时必须进入合并判断，不以多数票或“任一片段支持”直接输出最终科学标签。

## 4. 每类任务如何拆分与并行

| 任务 | 可并行单元 | 必须保留的依赖/归并 |
|---|---|---|
| 审稿分段 | 按原文位置切块，各块并行 | 局部保留说话人/轮次上下文；不清楚则unknown；最后按位置统一ID并处理重叠 |
| Checklist | 审稿人×轮次×局部意见块 | 每块配相关论文片段；统一问题ID，跨轮关系另做；长段落继续拆 |
| tone/review_dynamics | tone按段；dynamics按同审稿人、对象和范围的候选轨迹 | 必须保留时间顺序，不能把作者回复或沉默当审稿人认可 |
| core | 各正文块独立提取候选 | 全论文候选归并选择0—2核心后才映射共享claim；不读方法判断 |
| 两种基线 | 方法间、文中片段阅读、不同查询/下载并行 | 方法内部有科学依赖的分析步骤保留顺序，不能因加速改变适配方法定义 |
| 中立证据池 | 查询、引用解析、日期补全、下载 | 检索合并/排序后才确定全文名单，保持原预算与日期规则 |
| extract | 报告分段、方法之间 | 合并重复单位、保持全部冲突原句，统一unit_id；不依赖R或quality_checklist |
| reference | 核心之间、历史证据片段阅读 | 每核心综合比较与范围，形成R；不能汇总局部无发现成首次性 |
| support | 方法×断言小批次；必要时一个断言的不同证据阅读 | 按断言汇合后给最终支持及范围判断；批次不再附全部证据池 |
| novelty | 方法×核心 | 等相应R和P；各核心独立判断后按ID合并 |
| quality | 五个维度所需证据整理并行，方法间并行 | 全文综合维度保留整篇证据概览；跨贡献关系不得靠局部分数相加替代 |
| concerns | 方法×审稿问题小批次 | 分别保持对象覆盖、理由覆盖和分歧标签 |
| clusters | 六方法混合匿名单元分块提候选；候选簇比较并行 | 跨块同义簇必须对齐，不能简单拼接各块聚类；重要性独立判断 |
| fusion | 每条分支错误与Full候选对应并行；Full新增错误检查并行 | 确认“未传播”须检索完整Full范围；集合交并差由确定性代码计算 |
| preference | 论文×对手×AB/BA | AB/BA用相同中立材料、独立CLI；最终偏好保留整篇比较，不能简单对片段投票 |
| recheck | 论文×方法×评价类别/对象；差异解释各自并行 | 某对象第二次判断完成才解释分歧；不等待其他方法 |
| controls | 三类控制构造、各对原版/改版独立判断 | 构造完成后才评价；评价隐藏条件和配对另一侧；不改变控制数量 |
| export | 独立组件/格式转换并行 | 保持同一预生成论文bootstrap抽样；组件齐备后组panel再组母版 |

复核每篇的基础重复评价最多有6方法×3类别=18个独立任务，可进一步按对象拆分。最多36条对象分歧解释按各自结果动态加入。三类控制最多6个原版/改版判断也可独立调度。此数字是理论就绪任务上限示例，不是同时强制发起数；无对象、无合格控制和已有断点都会减少任务。

## 6. 调度器设计

- 单个脚本一个调度器，队列元素是最小可恢复工作单元，不再是包住几十次CLI调用的论文函数。
- 明确写出固定依赖表，不引入配置指纹、文件变化扫描、自动失效或自动重跑系统。执行清单与分片位置保存为普通JSON。
- 父任务不占CLI名额等待子任务。禁止每篇再开一个独立64线程池，禁止在同一已满线程池中阻塞等待新提交子任务。
- CLI、网络I/O、GPU、CPU分别限流；CLI名额只在启动会话前取得，结束即释放。等待网络/GPU不占CLI槽。
- 初始建议CLI上限64、网络I/O上限16、GPU共享单模型队列、CPU进程数不超过可用核数；这些是上限，不是强制同时运行数。按进程组RSS/可用内存和已观察服务错误调整准入，保留4 GiB余量。
- GPU继续共享模型并尽可能批处理，不盲目多进程复制显存。网络遵守真实限流/Retry-After；不假设本地内存充足就等于远端允许无限并发。
- 以持续补充就绪任务的方式填满可用槽，按论文/方法轮转，避免某一篇的大量小任务饿死其他任务。
- 状态区分pending、ready、running、succeeded、reused、blocked、failed、cancelled。只有succeeded/reused释放依赖。失败仅影响其后代，其余任务继续。
- 所有生成仍是独立Codex CLI会话，保留Luna和既定角色强度，不通过降模型/降推理强度掩盖调度问题。

## 7. 日志、中断、断点与旧结果

- 请求开始记录stage/paper/method/object/batch、材料字节数/字符数、正文块数量、去重节省量、估算tokens、CLI进程组与会话ID。
- 持续保存CLI JSONL事件和stderr，记录首事件、最后事件、耗时、退出原因和原始回答。长时间无事件标为“等待/无可见事件”，不伪称模型进度百分比，也不单凭静默判死。
- 心跳分别报告成功、复用、失败、阻塞、排队和在途，以及最近完成的子步骤。提供请求耗时分位数、吞吐、峰值RSS，供后续pilot判断并发是否有效。
- 超大请求在启动前拆分；长耗时请求保留失败尝试并缩小对象/材料分片后显式重试。先用小请求pilot测量延迟，再确定分类超时，不能把所有任务一律等待30分钟当作加速方案。重试次数有界。
- 第一次中断停止新任务并给予短暂落盘时间；再次中断/超时回收本次脚本创建的整个CLI进程组，记录cancelled，保留事件和已完成步骤。
- 每个成功子任务单独原子落盘，写入者唯一；续跑只补缺失子任务，不重读模型已成功完成的其他分片。已有文件无法解析单独报错，不自动删除。
- 请求按独立attempt保存日志，再汇总；不要把大段raw回答和所有进程日志集中竞争写一个大JSONL。旧11条坏日志保留原文与行号，解析其余记录，成本注明未知/不完整，不能按零计算。
- 新执行目录与旧试运行目录分开。原论文、共享claim及四方法原报告可复用；两基线按是否修改生成条件显式决定整批复用或重做。
- 已改变材料组织或评价协议的模型结果，不静默复用为新条件结果。选择新条件重跑pilot5相关评价；旧结果保留用于诊断。普通文件存在即续跑规则只在已明确选择的同一运行目录内适用。
